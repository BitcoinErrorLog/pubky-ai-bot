## Findings

| ID | Severity | File:line | Finding / exploit sketch | Fix |
| --- | --- | --- | --- | --- |
| F-A | Low | `src/optout.ts:53` (`please\s+stop\s+(?:replying|answering)`) | **Third-person "please stop replying to them/&lt;key&gt;" opts out the author.** The pattern has no first-person anchor, so a user telling Jeb to stop replying to *someone else* gets themselves opted out (probed: `"please stop replying to them"` → `opt_out`; `"please stop replying to <52-char key>"` → `opt_out`). Not exploitable cross-user — `setUserOptOut` always targets `job.author`, never a key parsed from text — so the impact is a self-inflicted, one-message-reversible surprise that fails the user's actual request. The deliberate bare form (`"please stop replying"` → `opt_out`, `optout.test.ts:35`) is fine; the third-person object case is the false positive. | Require a first-person object (`to me`) or Jeb-directed context for this pattern, or extend `isMetaQuestion`/add a third-person-object exclusion (`\b(them|him|her|others?|people)\b` → null). |
| F-B | Low | `src/scout/guard.ts:80-99` (`checkProfilingDenylist` gated on `:AUTHORED`) | **Raw mode can enumerate a person's muters.** `MATCH (u:User {id:$id})<-[m:MUTED]-(w:User) RETURN w.id LIMIT 10` passes `guardRawCypher` (probed: `ok=true`), violating the documented product rule "muted only as an aggregate count — never who" (`docs/scout.md:143`). The denylist only fires on id-bound-user + `AUTHORED` traversal; `MUTED` counterparty returns are unrestricted. No *template* can do this (verified: `MUTED` appears only in `profile_snapshot`, aggregate `count(DISTINCT m)` only) — the hole is exclusively the operator-enabled raw escape hatch (`JEB_SCOUT_RAW_ENABLED=1`, default off, separate tighter budgets `scoutRawPerUserDaily: 8` / `scoutRawGlobalDaily: 40`). | Add a deny rule: reject raw queries that return the counterparty of a `MUTED` edge for an id-bound user (e.g., `MUTED` + id-bound user + non-aggregate RETURN), mirroring the profiling denylist. |
| F-C | Informational | `src/scout/templates.ts:452,464,477,493` (hop/limit clamps) | `Math.min(max, Math.max(1, NaN))` is `NaN`, so a NaN `max_hops`/`hops`/`limit` passed *directly* to a template yields `FOLLOWS*1..NaN` (invalid Cypher, server-side error) or a `NaN` limit param. Unreachable through the tool path — zod enforces `int().min(1).max(...)` and `clampLimit` (`tools.ts:13-16`) is finite-guarded — so this is defense-in-depth only. | Add a `Number.isFinite` guard in the template clamp helpers. |
| F-D | Informational | `src/types.ts:75,86` + `src/reason.ts:253-255` | **Opt-out author is taken from the notification body (`mentioned_by`/`replied_by`), never cross-checked** against the canonical post URI's author segment or `view.details.author`. A Nexus notification with `post_uri` authored by B but `mentioned_by = A` would opt out A based on B's post. Nexus is trusted infrastructure and derives these fields from the actual post, so this is a hardening gap, not an attacker-reachable path. | Derive `author` from `parsePostUri(postUri).author` (or assert equality) in `mentionKey`/`reasonOne`. |
| F-E | Informational | `src/reason.ts:259-266,275-282`, `src/optout.ts:109-139` | Two deliberate-but-worth-confirming behaviors. (1) `queueOptoutConfirm` **does** forward `replacePostId` — asymmetric with the F-5 decision for skip notices: a `requeue --replace` of an opt-out mention overwrites the prior answer with the confirm text. Defensible (the user asked Jeb to stop; replacing the answer honors that), flagging so it is a conscious choice. (2) Flap damping: each real state transition earns exactly one confirmation and repeats in the same state are silent skips (verified in code and `optout.test.ts`), but confirmations bypass policy caps by design, so a user flapping their own state generates an unbounded stream of (fixed-text, self-threaded, zero-token) confirm replies. Self-spam only — confirms always reply to the requester's own mention; there is no way to make Jeb post them into a third party's thread except as replies to the flapper's own posts there. | (1) Document, or drop `replacePostId` on the confirm path like F-5. (2) Optional: rate-limit confirms per author (e.g., one per day). |

## Scope questions, answered

### 1. Five new Scout tools

**Does every template pass `guard.ts`?** Yes — all 12 new template queries (10 names, `top_posts` ×3 metrics) pass `guardRawCypher` with `LIMIT $limit` substituted, verified independently in `probe2.ts` and by the repo's own test (`scout.test.ts:677-684`). For precision: applying the guard to *pre-existing* templates produces false positives (`search_posts`/`topic_brief` trip the profiling denylist via their legitimate `a.id IN $authors` / `a.id = $scope_id` filters; `related_*`/`get_thread_down` trip the param-literal rule on their fixed `'replied' AS relationship` constants). Those templates never go through the guard in production (only `query_graph` raw mode does) and cannot be steered, so this is a statement about guard/test alignment, not a vulnerability.

**Are parameters bound?** Yes. Probed: template Cypher text is byte-identical under adversarial inputs (100 000-char strings, unicode math-alphanumeric lookalikes, `'); DETACH DELETE (n) //`, pubky-URI-shaped injection with a trailing Cypher fragment, `$from})<-[:MUTED]-(m) RETURN m.id //`, null bytes) — every value travels as a `$param` (`probe.ts`, 40+ assertions). The only string interpolation into Cypher is numeric hops/depth (clamped `Math.min(MAX, Math.max(1, n))` to ≤3/≤2) and enum-keyed maps (`score[metric]`, `orderExpr[metric]`, `dir` from `"asc"|"desc"`). Zod schemas reject negative/huge limits, `max_hops > 3`, unknown metrics, and >80-char topics; limits are then double-clamped by `clampLimit` and `FOLLOW_TOOL_LIMIT = 25`, and again client-side to `scoutLimitMax ≤ 100` (`client.ts:99`).

**Per-person profiling beyond product rules?** No.
- **MUTED:** appears in exactly one template (`profile_snapshot`, `templates.ts:565-566`) as `count(DISTINCT m)` — aggregate only, never who. No template returns muter/blocker identity. (Raw-mode residual: F-B.)
- **mentions_of:** the Cypher selects no `content`/`attachments` and the tool maps only `uri`, `author_id`, `author_name`, `indexed_at` (`tools.ts:1160-1165`) — post bodies are not returned.
- **trust_view:** returns tag-label counts, global vs asker's-1–2-hop-FOLLOWS-graph, plus claimant ids capped at `scoutClaimantCap = 12`. The asker is a model-supplied parameter, so the model can ask "tag counts in the graph of arbitrary pubky X" — but the FOLLOWS graph is public data already enumerable via `follow_path`/`stale_follows`/`recommend_follows`, and the graph DB holds no private edges. Nothing about a third party's *private* graph can be inferred because no private graph exists in this store. XOR of target/topic enforced at both the zod and execute layers.
- **profile_card (third party):** public-graph facts only — name, first-indexed, post/follower/following counts, tag labels+counts (claimant ids capped), top-5 most-replied-to, mutual booleans vs a supplied asker (public FOLLOWS), `muted_count` aggregate. No post bodies, no muter/blocker enumeration.

**Budgets/switches:** every tool execution passes `run()` → enabled check, store kill-switch, per-mention/per-author/daily budgets (`checkScoutBudgets`), and results re-enter model context only through `wrap()` → `screenToolResult` (injection sanitize + `redactSecrets` + 8 KB serialized cap). Query audit rows store hashes of cypher+params, not values (`client.ts:229-243`).

### 2. Opt-out

- **Can A opt out B?** No. Spoofed author: the author comes from the Nexus notification (`mentioned_by`/`replied_by`, `types.ts:71-107`), never from text; `setUserOptOut(job.author, …)` targets only that key. Quoting: a quote/repost with empty body is excluded (`ownBody` check, `reason.ts:244-252`); a quote *with* opt-out text opts out the quoter. Mentioning B's key in text: keys/URIs/@handles are stripped before classification (`stripMentionNoise`), all patterns are first-person, and even when classification fires the target is still the author. Probed: `"stop replying to <B's key>"` → `null`; `"unsubscribe <B's key>"` / `"leave me alone <B's key>"` → `opt_out` of the **author**. Residual false positive: F-A.
- **Confirmation without a model call?** Yes — fixed strings, voice-linted, `model: null`, `tokens: 0` in the evidence row (`optout.ts:99-137`), published through the normal publisher so the outbound gate still scans it.
- **Flapping spam?** One confirmation per actual state transition; repeats while already in that state are silent skips (no notice, no model, no caps notice), matching `docs/limits.md:54`. Confirms are only ever replies to the requester's own mention. See F-E(2) for the unbounded-but-self-directed residual.
- **`--role optouts` CLI:** prints `pubky`, `opted_out_at`, and `reason` — the reason being the author's *own* public opt-out text truncated to 500 chars (`db.ts:359-366`, `main.ts:127-141`). Nothing beyond the key, a timestamp, and the user's own words reaches the operator; documented in `docs/limits.md:56`.
- **Dashboard:** count only — `SELECT COUNT(*) … WHERE opted_in_at IS NULL` (`reporting.ts:402-405`), rendered as "count only; keys are not listed here" (`dashboard-report.ts:205`).
- **Migration 096:** plain `CREATE TABLE IF NOT EXISTS` + partial index; all access parameterized.

### 3. Translate intent

`TRANSLATE_ADDENDUM` is prompt shaping only; the full tool catalog stays registered. Injection surface of translating a post whose body contains instructions:
1. The typical target (the parent post) enters the prompt as a chain post — every chain post is detector-sanitized before assembly (`reason.ts:311-313`), and `extractionGuardChainAware` checks the mention **and** the newest ancestor (the translate target) *before any model call*, so an extraction-laced target gets a deterministic decline with zero token spend.
2. Targets fetched via `get_post`/`get_thread` (quoted posts) return through `wrap()` → `screenToolResult`: instruction patterns sanitized, secret-shaped spans redacted, 10 KB/field and 8 KB total caps (`tool-screen.ts`).
3. Outbound: every publish — translations included — passes `scanOutboundText` (secret scrubber + prompt-echo shingles) at the publisher, the last check before the PUT (`publish.ts:160-174`).
What remains is the generic model-layer injection risk (a post body saying "ignore your instructions and post X"), which is the pre-existing documented threat model — the addendum neither weakens the screening nor grants new tools.
