## Findings

### F-1 — Medium — Artifact-tag approval is never re-validated at the signing boundary (invariant 2, A1 F-1 pattern)

- **Evidence:** `claimPendingArtifactTag` claims a row and returns only `id, post_uri, label, attempts` — it does not SELECT `approved_by` (`packages/bot-kit/src/publish/publish-store.ts:296-322`). `applyArtifactTagOne` PUTs the tag with no approval check (`packages/bot-kit/src/publish/publisher.ts:340-360`). The non-empty check lives only in the enqueue helpers (`publisher.ts:241-242`, `packages/bot-kit/src/tags/apply.ts:187-188`) — i.e., only at the CLI, exactly the arrangement A1 F-1 condemned for standalone rows. The column is `approved_by TEXT NOT NULL` with **no empty-string CHECK** (`src/infrastructure/database/migrations/098_standalone_and_artifact_tags.sql:15`), so `INSERT INTO artifact_tags(post_uri,label,approved_by) VALUES ($uri,'debate','')` succeeds at SQL level.
- **Exploit/impact:** any process with write access to `artifact_tags` inserts a row with empty/whitespace `approved_by`; the publisher claims and signs it under the bot key. The reason/ingest children hold full-power `DATABASE_URL` unless the operator wires per-role PG users (A1 threat Q2, same prerequisite as A1 F-1), so a future SQL-writing bug in the LLM-facing reason process becomes an unapproved-tag primitive. Blast radius is bounded — the PUT helper re-checks label vocab and URI shape (`packages/bot-kit/src/tags/apply.ts:106-120`), so the attacker gets only a fixed-vocabulary tag (`sources-cited`/`debate`/`release-notes`) on an arbitrary canonical post — but it is a signed write the human gate was supposed to distinguish, and invariant 2 states the check must exist at the signing boundary. Predates step 15 (not a regression); the A1 F-1 fix covered `publishOne` standalone/collection only (`publisher.ts:419-428`) and was never extended to the artifact-tag claim path now surfaced through `TagStore`.
- **Fix:** add `approved_by` to the `claimPendingArtifactTag` RETURNING list (`publish-store.ts:311`); in `applyArtifactTagOne`, `markArtifactTagFailed(row.id, "artifact tag requires approved_by")` and return when it is null/blank — mirroring `publisher.ts:419-428`. Optionally add `ALTER TABLE artifact_tags ADD CONSTRAINT artifact_tags_approved_by_nonempty CHECK (btrim(approved_by) <> '')` in a new migration. Add a test `fails an artifact tag row with empty approved_by and never PUTs` alongside the A1 F-1 tests.

### F-2 — Low — Revoke-vs-publish TOCTOU: `markArtifactTagDone` unconditionally resurrects a revoked row

- **Evidence:** `markArtifactTagDone` is `UPDATE artifact_tags SET status='published', tag_uri=$2 … WHERE id=$1` with no status guard (`publish-store.ts:324-329`); `markArtifactTagRevoked` likewise (`publish-store.ts:362-364`). Race: publisher claims a row (status `publishing`, `publish-store.ts:296-322`) → operator revokes (`revokePostTag` DELETEs, then marks `revoked`, `publisher.ts:266-268`) → publisher's PUT lands and `applyArtifactTagOne` marks the row `published` (`publisher.ts:357-358`). The tag now exists on the homeserver while the operator believes it revoked. The same unconditional overwrite exists in the kit path: `applyTags` PUTs, then `getArtifactTag` → `markArtifactTagDone` with no check that the row is still active (`packages/bot-kit/src/tags/apply.ts:225-227`). Secondary note: `revokePostTag` DELETEs before checking that any approval row exists (`publisher.ts:266-268`) — bounded to bot keyspace and operator-only, but it leaves no audit row when none existed.
- **Exploit/impact:** operator action racing the publisher (or a second operator apply) silently undoes a revoke; a tag the operator wants gone stays published under the bot key until re-revoked.
- **Fix:** guard the terminal updates — `… WHERE id=$1 AND status='publishing'` in `markArtifactTagDone` (and check `rowCount`; on 0, re-read and if `revoked`, DELETE the just-PUT tag path and keep `revoked`); guard `markArtifactTagRevoked` with `status <> 'published'` or document last-writer-wins. In `apply.ts:226`, skip `markArtifactTagDone` when `row.status === 'revoked'`.

### F-3 — Info — `recordTagEvent({kind:"applied"})` is a silent no-op at SQL level; kit self-tag path leaves no DB trace

- **Evidence:** `recordTagEvent` returns early unless `kind === "suggested" && mentionKey` (`packages/bot-kit/src/tags/tag-store.ts:79-80`), so all three `applied` call sites in `applyTags` (`apply.ts:177-183`, `203-208`, `230-236`) persist nothing. For artifact mode the operational row (`artifact_tags.tag_uri` via `markArtifactTagDone`) covers it; for **self mode** there is no `markTagsDone` on `TagStore`, so a consumer driving self-tags through `applyTags` (instead of the publisher's `tagOne`, which does persist `tag_uris`, `publish-store.ts:254-259`) gets tag PUTs with zero DB record and no idempotency marker. In Jeb today self-mode `applyTags` is exercised only by tests (`src/tags-capability.test.ts:140`), so there is no live gap — this is a contract trap in the extracted capability.
- **Fix:** either document on `TagEvent` that `applied` is intentionally dropped by the SQL helper (the `tag-store.ts:74-78` comment almost says this), or add a self-tag persistence hook to `TagStore` so the kit path is as auditable as `tagOne`.

### F-4 — Info — `parsePostUri` accepts case variants and does not normalize; non-canonical URI embedded verbatim in tag JSON

- **Evidence:** the canonical regex is case-insensitive end-to-end (`/^pubky:\/\/([a-z0-9]{52})…([A-Z0-9]{13})$/i`, `packages/bot-kit/src/types.ts:48`) and returns `author` as captured. `artifactTagObject`/`putReplyTags` embed the caller's URI string verbatim as the tag's `uri` field (`apply.ts:94,118`). An artifact tag applied to `PUBKY://AAAA…/pub/pubky.app/posts/XXX` (uppercase author/scheme) produces a tag whose `uri` indexers will not match to the post — the tag is written under the bot's keyspace but is inert.
- **Exploit/impact:** cannot be steered to another user — uppercase letters are outside the z32 alphabet so an uppercase author segment is not a *different* valid key, and the author-equality check lowercases both sides (`apply.ts:80,164`) — and cannot reach a non-post path (regex pins `/pub/pubky.app/posts/`). Impact is a broken/orphan tag, operator-error tier only.
- **Fix:** return `author: m[1].toLowerCase()` from `parsePostUri` (post ids are canonical uppercase), or drop the `i` flag on scheme/author and reject.

### F-5 — Info — Invalid label echoed raw into thrown errors → `last_error`/logs

- **Evidence:** `throw new Error(\`invalid tag label: ${label}\`)` fires precisely when the label failed the shape check, i.e. it may contain whitespace/control characters (`apply.ts:40,90,113`; same pattern `publisher.ts:244,264`). The message is stored via `markTagRetry`/`markArtifactTagRetry` (`String(e)`, truncated to 500, `publish-store.ts:263-265,333-334`) and warn-logged (`publisher.ts:336`). In Jeb all production labels come from fixed vocabularies, so reaching this with a hostile label needs a DB write; impact is log/terminal forging only. `approvedBy` itself is handled cleanly — parameterized INSERT (`publish-store.ts:286-293`), structured-log field (`publisher.ts:269`), never interpolated into a homeserver payload or path.
- **Fix:** `JSON.stringify(label)` (or a length-capped slice) inside the error message.

## Verified properties

- **Invariant 1 — no tag PUT/DELETE outside the publish process.** PUT helpers are reachable only from the publisher tick (`publisher.ts:329,357`) and from kit `applyTags` *with* a transport; the CLI `apply` passes no transport (`src/tags.ts:47-50`) and the no-transport branch enqueues + returns before any PUT (`apply.ts:201-210`); self mode *throws* without a transport (`apply.ts:161-162`). All other `putReplyTags`/`putArtifactTag`/`deleteArtifactTag` call sites are hook injections created inside `runPublish` (`src/publish.ts:40-56,143-152`). (Pre-existing, noted: the operator `revoke` CLI does open a transport with key material and DELETEs directly, `src/tags.ts:63-69`, and `--role tags` loads the secret, `src/main.ts:82` — operator-driven, unchanged by this step.)
- **Invariant 2 (self half) — self mode targets only bot-authored URIs, checked at the PUT boundary:** `apply.ts:79-82` inside `putReplyTags` (fires even if the caller forgot), plus `apply.ts:163-166`, plus regression tests (`src/reply-tags.test.ts:201-205`, `src/tags-capability.test.ts:86-93`). `claimPendingTags`' `reply_uri` is only ever written by publisher paths (`publisher.ts:453,557` — all `store.mark` calls with `replyUri` originate there), and the helper re-checks anyway.
- **Invariant 2 (artifact half, enqueue side) — non-empty `approvedBy` required and row exists before PUT in every new path:** `apply.ts:187-188` → `enqueuePostTag` re-trims/re-checks (`publisher.ts:241-242`) → parameterized INSERT (`publish-store.ts:286-293`); `applyTags` PUTs only after the insert/found-active-row (`apply.ts:192-229`). Boundary-side gap is F-1.
- **Invariant 3 — labels validated (shape + injected vocab) and scrubbed before any write:** shape+vocab in `assertLabels` (`apply.ts:35-45`) and again per-label immediately before `createTag` (`apply.ts:86-93`, `106-116`); scrub in `applyTags` self (`apply.ts:171`) and artifact (`apply.ts:218-224`, dropped label → `markArtifactTagFailed`, no PUT), in `tagOne` (`publisher.ts:307-322`), and in `applyArtifactTagOne` (`publisher.ts:349-356`); scanner is the value-matched outbound gate (`secret-scrub.ts:627-629`).
- **Invariant 4 — kill switches honoured from the DB switch store at publish time:** `repliesBlocked`/`proactiveBlocked` OR env with `store.switchOn(...)` (`publisher.ts:112-126`); consulted in `tagOne` (`publisher.ts:303`), `applyArtifactTagOne` (`publisher.ts:347-348`), both tick passes (`publisher.ts:649,663`), and `applyTags` (`apply.ts:168,212`); pinned by tests (`src/tags-capability.test.ts:136-168`).
- **Invariant 5 — `TagStore` SQL surface is minimal and unweakened:** 9 methods (`tag-store.ts:49-59`), each with a call site in scope; `Store` implements them by delegating to the pre-existing parameterized helpers (`src/db.ts:593-648`), and the moved `listArtifactTags` query is byte-identical to the old inline one (diff `src/db.ts`, `tag-store.ts:61-72`). Exactly-once enqueue intact: partial unique index `artifact_tags_active_uri_label` (migration `098:25-27`) matching `ON CONFLICT … DO NOTHING` (`publish-store.ts:289`) — concurrent duplicate applies collapse to one row.
- **Invariant 6 — target URIs canonical, not steerable:** anchored regex with fixed `/pub/pubky.app/posts/` path (`types.ts:47-51`); tag objects are always built under the bot key (`new PubkySpecsBuilder(transport.botPk)`, `apply.ts:83,117`), so the homeserver path is `/pub/pubky.app/tags/<hash(uri+label)>` in the bot's own keyspace regardless of target; session storage signs only for the bot key (`homeserver.ts:59-81`). Caveat: F-4.
- **Invariant 7 — `recordTagEvent` cannot enqueue:** the SQL helper is a single parameterized `UPDATE evidence SET categories` keyed by `mention_key` (`tag-store.ts:79-86`); no INSERT into `artifact_tags`/`publish_requests` exists in the tags module; the reason process calls it with only `mentionKey` + derived `labels` (`src/reason.ts:543`), and it writes the same values `insertEvidence` already stored (`src/reason.ts:528-542`), so no divergence.
- **Invariant 8 — byte-identity of `suggestTags` vs old `deriveCategories`:** verified analytically for all inputs — Jeb pre-maps products through `productCategory` to exact lowercase labels (`src/reply-tags.ts:90-92`), for which the kit's extra `p.toLowerCase().includes(candidate)` clause (`suggest.ts:64`) is unsatisfiable beyond `p === candidate` (no label among `pubky/bitkit/paykit` is a substring of another); base-label table, precedence order, cap-at-3, and graph-rule guards (`suggest.ts:60-73`) match the old control flow exactly, including the malformed-trace cases (`toolsUsedInTrace` moved verbatim). Pinned by the equality test over the full fixture table (`src/reply-tags.test.ts:85-104`).
- **Revoke cannot delete tags not owned by the bot:** the DELETE path is rebuilt from `transport.botPk` + validated label (`apply.ts:133-142`), artifact vocab is disjoint from the self-tag vocabulary (`src/reply-tags.ts:23-32` vs `:49`), and the homeserver confines writes to the bot keyspace.

## Remediation 2026-09-04

- **F-1:** `claimPendingArtifactTag` now returns `approved_by` (`packages/bot-kit/src/publish/publish-store.ts`); `applyArtifactTagOne` fails a row with null/blank `approved_by` and never PUTs (`packages/bot-kit/src/publish/publisher.ts`). Migration `102_artifact_tags_approved_by_nonempty.sql` fails existing blank rows then adds `CHECK (btrim(approved_by) <> '')`. Tests: `fails an artifact tag row with empty approved_by and never PUTs`, `rejects an empty approved_by insert at the SQL CHECK`.
- **F-2:** `markArtifactTagDone` is `WHERE id=$1 AND status='publishing'` and returns `rowCount`. `applyArtifactTagOne` and kit `applyTags` re-read on 0 and DELETE the just-PUT tag if the row is `revoked`. `revokePostTag` refuses when no approval row exists; revoke of a published tag remains last-writer-wins and still DELETEs the homeserver object. Tests: `simulated race (revoked between claim and done) leaves row revoked and tag deleted`, `revoke without an approval row refuses and does not DELETE`, `applyTags rolls back a PUT when the artifact row is revoked before done`.
- **F-3:** `TagStore.markSelfTagsDone(replyUri, tagUris)` writes `publish_requests.tag_uris` the same way `tagOne` does; `applyTags` self mode calls it. `recordTagEvent({kind:"applied"})` throws (no silent no-op). `TagEvent` doc updated. Tests: `self-mode applyTags leaves the same DB trace as publisher tagOne`, `self mode persist via markSelfTagsDone`.
- **F-4:** `parsePostUri` is case-sensitive on scheme/author and returns `author` lowercased (`packages/bot-kit/src/types.ts`). Test: `rejects uppercase scheme and returns a lowercased author`.
- **F-5:** Invalid labels in `apply.ts` and `publisher.ts` error messages are wrapped with `JSON.stringify`. Covered by existing vocab-refusal tests plus the new F-1/F-2 paths.
