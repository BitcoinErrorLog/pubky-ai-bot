## Specific questions posed

- **`nlq:` skip vs reason-loop keys — safe.** Reason rows' `mention_key` is the mention's post/reply URI: notifications pass `mentionKey()` (`bot-kit/types.ts:79-119`), which requires `parsePostUri` to succeed; `parsePostUri` (`bot-kit/types.ts:47-51`) pins `^pubky://[a-z0-9]{52}/pub/pubky\.app/posts/[A-Z0-9]{13}$` — anything else (including any string starting `nlq:`) returns null and is never enqueued (`ingest.ts:143-160`). The requeue CLI validates identically (`requeue.ts:57,85`), and the reason loop re-parses before use (`reason.ts:182`). A Pubky post URI always begins `pubky://`; the only producer of `nlq:` keys anywhere in the tree is `nlqMentionKey` (`nlq/http.ts:90-92`; grep-confirmed). An attacker cannot get an `nlq:`-prefixed key into `scout_queries` via the reason path.
- **Per-caller SQL** — parameterized (`budget.ts:80-84`, `mention_key = $1`) and uses the identical day boundary expression as the global count (`date_trunc('day', now())`, `budget.ts:82` vs `:91`; same as the shared 400/day ceiling at `:31`).
- **Token compare** — SHA-256 applied to *both* sides, equal-length 32-byte buffers into `timingSafeEqual` (`http.ts:63-67`).
- **403 path** — returns at `http.ts:128-131`, before `queryNlq` (`:133`); all Scout/DB work happens inside `queryNlq`. Per-request, zero Scout/DB work precedes the 403 (body read + JSON parse only). Startup refresh is process-level and now also switch-gated.
- **Whitelist coverage** — every code the stack can produce (`BUDGET`, `SCOUT_BACKOFF`, `RATE_LIMITED`, `SWITCH`, `DISABLED`, `QUERY_REJECTED`, `QUERY_TIMEOUT`, `INTERNAL_ERROR`, `SHAPE_ERROR`, `SCHEMA_ERROR`, `BAD_INPUT`, `HTTP_<status>`, arbitrary upstream strings) maps to a static whitelist member via the `SCHEMA_*` rule and the `upstream_error` catch-all (`client.ts:25-29`). Complete.
- **Switch-blocked tick stays fail-closed** — the tick returns before `refreshScoutSchema` (`schema-cache.ts:178-181`), so `source` is never mutated in that state; it stays non-`live` (planner refuses) rather than flipping to anything plannable.
- **No tight-loop** — initial `schedule(0)` is one-shot; all re-scheduled delays are `retryMs` ≥ 30 s or `interval`. `retryMs` never decreases except on success. `JEB_SCOUT_SCHEMA_REFRESH_MS` is `z.number().positive()` (`config.ts:73`), so 0 is rejected; an absurdly small positive value yields the same fetch cadence as the pre-remediation `setInterval` (not a regression). Mocked clocks advance through real delays; no zero-delay re-arm cycle exists.
- **`REASON_ALLOWLIST` removal** — git-verified: only the comment and `"JEB_NLQ_TOKEN"` were removed; all other `JEB_NLQ_*` and every other entry intact.

## New findings

**NF-1 — 403 check runs after body read/parse on a dangerous bind (Info).** `nlq/http.ts:106-131`: up to 1 MB is buffered and JSON-parsed before the bearer check. Bounded by `maxConnections` 128 and `requestTimeout` 30 s, so worst case ~128 MB transient. *Fix:* evaluate `nlqRequiresBearer(bind) && !nlqBearerMatches(req)` before `readBody(req)`.

**NF-2 — Positive auth path on a non-loopback bind is untested (Info).** `process.test.ts:167-197` proves missing/wrong bearer → 403, and `:133-139` unit-tests the matcher, but nothing asserts correct bearer + `JEB_NLQ_BIND_DANGEROUS=1` → 200. A regression making `nlqBearerMatches` always-false would lock out legitimate callers with all tests green. *Fix:* add the positive case to the dangerous-bind test.

**NF-3 — `BAD_INPUT` is now mislabeled `upstream_error` (Info).** `tools.ts:626,1078` throw local input-validation errors; `publicScoutErrorCode` (`client.ts:25-29`) maps them to `upstream_error`/"graph lookup unavailable right now". Static and safe, but the reason-loop model sees "upstream failure" for its own malformed args (may retry identically), compounding the signal loss A4r already noted. *Fix:* whitelist `BAD_INPUT` with a static "invalid arguments" message.

**NF-4 — Per-caller daily count includes `ok = FALSE` rows (Info).** `budget.ts:80-83` has no `ok` filter (unlike the per-mention cap at `:40`). A caller behind a flaky upstream burns their own 200/day on failures; consistent with the already-accepted global-count semantics (A4r F-4 test bakes it in), fail-safe direction, but worth a doc line in `docs/nlq.md`. *Fix (optional):* document, or add `AND ok = TRUE` if failed calls shouldn't tax the caller.
