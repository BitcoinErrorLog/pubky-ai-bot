# KIMI EXTERNAL AUDIT A2 — Proactive Drafts Module + DB Layer

Scope: `src/drafts/*.ts`, `src/db.ts` (full file, 1159 lines), `src/infrastructure/database/migrations/097_drafts.sql`, plus read-only verification of directly-called code (`publish.ts` enqueue/scrub/publisher-hook lines, `bot-kit/scout/*`, `links.ts`, `voice.ts`, migrator). `src/publish.ts` itself is covered by a separate audit. Read-only worktree; no source modified.

## Verdict: FIX-FIRST

The core safety invariant holds — no autonomous path from draft to `publish_requests` exists, approve is replay-safe, and all in-scope SQL is parameterized. Two findings should be fixed before enabling proactive drafts in production: the approve-time daily cap is raceable across concurrent approves (F-1), and attacker-controlled graph text is embedded raw into publishable bodies with newline/markup/link injection possible (F-2). The remainder are low-severity hardening items.

## Threat question answers (summary)

1. **Autonomy** — No code path reaches `publish_requests` without operator approve. The only `enqueueStandalonePost` caller outside tests is `approveDraftToPublishRequest` (src/drafts/publish-request.ts:39). Draft→`published` transitions are guarded in SQL (`status='approved' AND decided_by IS NOT NULL AND decided_by <> ''`, src/db.ts:1087, src/db.ts:1100). `no-autonomous.ts` is only a test-time tripwire (sole caller: src/drafts/drafts.test.ts:335), not a runtime guard — its claim is backed by db.ts, not by its own scan (F-3).
2. **Provenance** — No draft-time screening for injection or secrets; only style lint + citation cap (src/drafts/finish.ts:26-27). Secrets/prompt-echo are screened once, at the publish-time outbound gate (src/publish.ts:372-384). Markup and fake-`pubky://` link injection into drafts is possible (F-2). No LLM is in the generation loop, so model-level prompt injection is N/A in-module.
3. **Approval integrity** — Approve is not replayable (row lock + status recheck, src/db.ts:1013-1022; content-hash dedupe index). No in-code path edits a draft body between show and approve, but the enqueue uses a pre-transaction read (F-4). Draft id is validated and parameterized (src/drafts/cli.ts:79-82, src/db.ts:975). Concurrent approves of *different* drafts defeat the daily cap (F-1).
4. **SQL** — All in-scope queries parameterized; interpolated fragments are constant strings with `$n` values (src/db.ts:201-214). The `publish_requests(mention_key)` partial unique index (migrations/050:31-33) matches the ON CONFLICT target (src/db.ts:505) and preserves exactly-once. Gap: no unique constraint backing the per-day proactive cap (F-1). Migration runner's session-level `pg_advisory_lock` correctly serializes concurrent migrators (src/infrastructure/database/migrator.ts:52-63); per-migration transactions (migrator.ts:88-96); 097 is idempotent.
5. **Scout usage** — Generators never call the client directly; all calls go through `createScoutTools` wrappers (src/drafts/generate.ts:39-45) enforcing config enable, env+store kill switch, daily ceiling and per-mention cap (src/bot-kit/scout/tools.ts:228-249, src/bot-kit/scout/budget.ts:25-65), with the circuit breaker inside the client (src/bot-kit/scout/client.ts:97). `release_radar` calls the GitHub API directly (src/drafts/release-radar.ts:33-38) and `stats` calls Nexus directly (src/drafts/stats.ts:32-33) — neither is Scout; acceptable.

## Findings

### F-1 — MEDIUM — Proactive daily cap is raceable across concurrent approves of different drafts

- **Where:** src/drafts/publish-request.ts:30-33 (pre-check); src/db.ts:1013 (locks only the target draft row `FOR UPDATE`); src/db.ts:1023-1031 (in-transaction cap count); src/infrastructure/database/migrations/097_drafts.sql:20-22 (`idx_drafts_proactive_day` is non-unique).
- **Exploit path:** Operator (or two operator shells / a scripted CLI) runs `--role drafts approve` for draft A and draft B concurrently. Each transaction row-locks a *different* drafts row; both cap-count statements execute before either commits, so under READ COMMITTED both see "0 approved today"; both enqueue via `enqueueStandalonePost` and both commit. Result: 2 approved proactive posts in one UTC day despite `JEB_PROACTIVE_MAX_PER_DAY=1` (src/drafts/types.ts:57). The cap is the module's headline safety promise and exists only as a read-then-write check. Existing test coverage is sequential only (src/drafts/drafts.test.ts:286-327), so the race is unexercised.
- **Fix:** Enforce the cap in the database: `CREATE UNIQUE INDEX ... ON drafts (proactive_utc_day) WHERE status IN ('approved','published')` (the second concurrent UPDATE blocks on the index until the first commits, then fails), or take `pg_advisory_xact_lock(<constant>)` inside `approveDraft` before the cap count. Keep the friendly error mapping for the unique violation.

### F-2 — MEDIUM — Attacker-controlled graph text embedded raw into publishable draft bodies (markup / newline / fake-link injection)

- **Where:** src/drafts/what-changed.ts:21 (post `content_preview`, whitespace-collapsed, 120 chars, embedded raw); src/drafts/thread-worth-reading.ts:25 (180 chars, raw); src/drafts/the-disagreement.ts:30 (cluster `label` embedded raw, **not** whitespace-collapsed, inside quotes); src/drafts/new-connection.ts:35,47 (emerging-topic `label` into body and title); src/drafts/finish.ts:26-27 (only `lintVoice` + `rewritePubkyCitations`); src/voice.ts:134-141 (citation cap counts *any* URL, drops those past 3); src/links.ts:26-41 (rewrites any `pubky://` URI or bare 52-char pk in the text into first-class `https://<appUrl>/post|profile/...` links).
- **Exploit path:** Any pubky user writes a post (or applies a tag label) about a watched topic ("pubky" is the default topic, src/drafts/what-changed.ts:12) containing crafted text — e.g. a markdown link `[docs](https://phish.example)`, a newline-bearing tag label that injects whole lines into the "The disagreement" side list, or a fake `pubky://<52ch>/pub/pubky.app/posts/<id>` that `rewritePubkyCitations` promotes to an official-looking app citation under the bot's own app URL. Scout indexes it; the next `drafts generate` embeds it verbatim into a draft body; after operator approve it is published under the bot key. Attacker URLs also consume the 3-citation cap and can push the legitimate evidence links out of the body (cap drops later URLs, src/voice.ts:134-141). The only controls are operator eyeballs on `show` JSON output and the publish-time secret scrubber (which targets secrets/prompt-echo shingles, not markup or misleading links — src/publish.ts:372-384).
- **Fix:** Sanitize all graph-sourced strings at the `finishDraft` boundary: strip newlines/control chars from labels and titles (mirror the `replace(/\s+/g," ")` treatment already used for previews), escape or neutralize markdown link/image syntax in untrusted segments, and emit legitimate evidence links before any attacker-influenced text so the citation cap cannot evict them. Keep label character whitelists consistent with the query-side tag sanitizer (src/bot-kit/scout/tools.ts:278).

### F-3 — LOW — `no-autonomous.ts` is a test-only tripwire with a hardcoded, incomplete file list and an evadable regex

- **Where:** src/drafts/no-autonomous.ts:11-22 (scanned files: omits `stats.ts`, `scout-util.ts`, `types.ts`, `index.ts`, and any future file added to the directory); no-autonomous.ts:23 (regex requires the literal quoted string `'published'`); sole caller src/drafts/drafts.test.ts:335 (CI only — nothing invokes it at process start).
- **Exploit path:** Not directly exploitable — the runtime boundary is real (see below). But the guard gives false confidence: a future generator file (or an edit to `stats.ts`/`scout-util.ts`) that writes `status: 'published'` is invisible to the scan, and trivial obfuscation (`'pub'+'lished'`, template literals, SQL built from concatenation) evades the regex even in scanned files.
- **Mitigating fact (verified):** runtime enforcement is sound — `markDraftPublished`/`markLinkedDraftPublished` require an approved row with non-empty `decided_by` in the UPDATE's WHERE clause and throw/no-op otherwise (src/db.ts:1084-1103); the only transition to `approved` is `approveDraft`, which demands `decidedBy` and runs inside the operator-invoked transaction (src/db.ts:1004-1067); `enqueueStandalonePost` rejects empty `approvedBy` (src/publish.ts:94-95); the publisher marks drafts published only after a successful PUT (src/publish.ts:420-437).
- **Fix:** Build the scan list from a directory read (or move the invariant into the database: `CHECK (status NOT IN ('approved','published') OR decided_by IS NOT NULL)` on `drafts`), and invoke `assertNoAutonomousDraftPublish()` at role startup rather than only in tests.

### F-4 — LOW — Approve enqueues a pre-transaction read of the draft body (TOCTOU hardening)

- **Where:** src/drafts/publish-request.ts:27-29 (draft read outside the transaction); publish-request.ts:38-44 (enqueue closure captures `existing.body`); src/db.ts:1013-1022 (row locked `FOR UPDATE` and status rechecked, but the locked row's body is never used for the enqueue).
- **Exploit path:** Not exploitable today: no code path updates `drafts.body` (insert-only at src/db.ts:964-972; all draft UPDATEs touch status/decision columns only — src/db.ts:1039-1049, 1069-1078, 1084-1103). If any future "edit draft" feature lands, the operator would approve the body shown by `show` while a concurrent edit swaps content before the lock, and the stale-or-swap ambiguity is resolved by whichever read happened first — approval integrity then depends on caller discipline rather than the lock.
- **Fix:** Have `approveDraft` pass the locked row (`current.body`, src/db.ts:1018) to the enqueue callback so the approved bytes and the enqueued bytes are the same row version.

### F-5 — LOW — Approving a second draft with an identical body is a silent no-op that links the old request; both drafts end up "published" from one post

- **Where:** src/publish.ts:98-100 (`mention_key = standalone:sha256(seed)`, seed is content+kind+attachments+collectionId); src/db.ts:505 (`ON CONFLICT ... DO NOTHING`); src/db.ts:995-1001 (`publishRequestIdForMention` returns the pre-existing row id); src/db.ts:1039-1049 (draft linked to that id and marked approved); src/db.ts:1097-1103 (`markLinkedDraftPublished` flips *every* draft holding that `publish_request_id`); dedupe index migrations/050_work_queue_dedupe.sql:31-33.
- **Exploit path:** Exactly-once publishing holds (the partial unique index prevents a second active row — verified). The quirk is integrity/UX: operator approves draft B (identical body to already-approved draft A), receives a success line with a `publish_request_id` that belongs to A, burns the day's cap slot (F-1 check counts B), and no new post is ever queued; when A's request completes, B is also marked `published`. Because `'published'` is inside the partial index, identical content can never be re-posted later even if the operator intends to.
- **Fix:** When `enqueue` reports `inserted === false`, roll back with an explicit "identical content already queued/published as request #N" error instead of linking the existing request; or add a `force` flag that appends a nonce to the seed when a deliberate re-post is desired.

### F-6 — LOW — A secret-scrubbed draft is still marked `published`, and stats measure the decline post's reception

- **Where:** src/publish.ts:372-384 (scrub gate substitutes `SECRET_DECLINE_REPLY` for the row content); src/publish.ts:437 (`markLinkedDraftPublished` runs unconditionally for standalone rows); src/db.ts:1097-1103; src/drafts/stats.ts:60-80 (reception measured on the published request's post).
- **Exploit path:** If a draft body trips the outbound scrubber (e.g. an attacker baits a secret-shaped string or a prompt-echo shingle into a post preview — see F-2), the bot publishes the decline text, yet the draft row flips to `published`. Operator-facing stats then show the format as published and score the decline post's replies/reposts as the draft's "reception," masking the fact that the approved content never appeared.
- **Fix:** Skip `markLinkedDraftPublished` when the row was scrubbed/declined (or record a distinct terminal status such as `declined`), and exclude such rows from reception stats.

## Non-findings (verified clean)

- **Replay of approve:** same draft cannot be approved twice — status transition guard under `FOR UPDATE` (src/db.ts:1013-1022); rejected drafts are terminal (src/db.ts:1071-1072); `markDraftPublished` requires approved+decided_by and throws otherwise (src/db.ts:1091-1093).
- **Draft id validation:** integer ≥1 enforced at the CLI (src/drafts/cli.ts:79-82, 90-93) and all lookups parameterized (src/db.ts:975, 1013).
- **SQL injection:** no user-controlled string interpolation in any in-scope query; the only template interpolation uses constant fragments with parameterized values (src/db.ts:201-214, 553); `listDrafts` status is allowlist-validated (src/drafts/cli.ts:60) and parameterized (src/db.ts:981).
- **Migration runner:** session-level advisory lock held across the whole run, unlock in `finally`, crash-safe via session teardown (src/infrastructure/database/migrator.ts:51-63); `._` AppleDouble files excluded from loading (migrator.ts:39); 097 uses `IF NOT EXISTS`/`IF NOT EXISTS` ALTERs throughout (097_drafts.sql:3-26).
- **Scout budget/circuit:** drafts generators consume the wrapped tools only; `run()` gates on config, switches, and budgets before every call (src/bot-kit/scout/tools.ts:228-249); breaker checked in the client (src/bot-kit/scout/client.ts:97); per-format `mentionKey` (`draft:generate:<format>`) gives per-mention cap accounting (src/drafts/generate.ts:42).
- **CLI gating:** generation requires `JEB_DRAFTS_ENABLED=1` plus per-format switches (src/drafts/cli.ts:35-44, src/drafts/generate.ts:17-23); the drafts role is reachable only via explicit operator CLI invocation (src/main.ts:129-131); no scheduler/cron path to `approve` exists.

## Remediation 2026-09-04

- **F-1** — Cap is configurable (`proactiveMaxPerDay`), so no unique index. `approveDraft` takes `pg_advisory_xact_lock(JEB_PROACTIVE_CAP_LOCK)` before the count (`src/db.ts:66`, `src/db.ts:829`). Test: `concurrent approves of different drafts on the same UTC day: exactly one succeeds`.
- **F-2** — `finishDraft` sanitizes titles/previews (control/newlines, markdown link/image/autolink URLs, `pubky://` + bare pubkeys) and prepends evidence hrefs (`src/drafts/finish.ts:28`, `src/drafts/finish.ts:38`, `src/drafts/finish.ts:88`). Label whitelist matches Scout (`packages/bot-kit/src/scout/tools.ts:278`). Tests: `neutralizes a markdown phishing preview and keeps evidence ahead of the citation cap`; `collapses a newline-bearing label so it cannot inject a list item`; `strips a fake pubky:// post URI in a preview so rewritePubkyCitations cannot promote it`.
- **F-3** — `no-autonomous.ts` directory-reads every `.ts` in `src/drafts/` (`src/drafts/no-autonomous.ts:24`); invoked at drafts-role startup (`src/drafts/cli.ts:30`). CHECK `drafts_decided_by_required` in migration `101`. Test: `no autonomous publish path in drafts modules`.
- **F-4** — `approveDraft` passes the `FOR UPDATE` row into enqueue; `approveDraftToPublishRequest` uses `locked.body` (`src/drafts/publish-request.ts:35-38`). Covered by the approve/enqueue tests.
- **F-5** — `inserted === false` rolls back with `identical content already queued/published as request #N` (`src/db.ts:856`). Test: `approve of identical content rolls back instead of linking the existing request`.
- **F-6** — Status `declined` (migration `101`); publisher calls `markLinkedDraftDeclined` when the outbound gate scrubbed the standalone row (`packages/bot-kit/src/publish/publisher.ts:519-520`, `src/db.ts:930`). Reception stats exclude non-published and scrubbed rows (`src/drafts/stats.ts:67`). Test: `outbound-gate decline marks the linked draft declined and excludes it from reception stats`.
