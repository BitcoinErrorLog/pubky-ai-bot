**Scope:** sensitive-area code on branch `stage0/modernize` (diff `main..stage0/modernize`, HEAD `54761bf`). jeb-slim excluded per instructions. Read-only audit; no files modified, no builds run, no secrets printed.

## Per-question notes

**1. Key material.** Loaded in `src/services/pubky.ts:157-200` from `PUBKY_BOT_SECRET_KEY_HEX` (preferred, 32-byte hex enforced) or `PUBKY_BOT_MNEMONIC` via `bip39.mnemonicToSeedSync(...).subarray(0,32)` → `Keypair.fromSecret`. Keypair and `Session` live in the `PubkyService` singleton for process lifetime — expected, but the *raw* mnemonic/hex additionally persist in `appConfig` and `process.env` forever (F6). No code path logs the secret: init errors are wrapped (`pubky.ts:194-199`), only the public key is logged (`:190`). Nothing serializes the keypair/session to disk; the session cookie never touches the HTTP surface, metrics, or LLM prompts (prompts contain only post content — `secure-prompts.ts`, `summary.ts`, `factcheck-websearch.ts`, `classifier.ts`). Derivation is a documented-but-nonstandard footgun (F7). Residual leak risk: Zod error echo (F6) and `.env` mounted into the dev container (F1).

**2. Session/auth.** `authenticateToHomeserver` (`pubky.ts:202-225`): signin first, signup-with-token fallback on *any* error (F12). Single session reused for all PUTs. No expiry handling (F3) — this is the main availability risk. Signup token held in env, never logged. `healthCheck` can re-auth only if `session` is null.

**3. Publish authorization.** Strong. The only live write is `publishReply` → `PubkySpecsBuilder(botPublicKey).createPost(...)` → `session.storage.putJson(meta.path, …)` (`pubky.ts:673-691`) — the path is SDK-derived under the bot's **own** `/pub/pubky.app/posts/{id}`; attacker input (`parentUri`) is embedded as post *content* (the `parent` field), not in the storage path. No `DELETE`/`storage.del` call exists anywhere in `src/`. No publish-under-other-identity path. The only non-posts write is the dead `updateBotProfile` (F11). Content is length-capped (800/1200 chars, `reply.ts:55,74`) and wordlist-checked (except canned mode, F15).

**4. Prompt injection / untrusted data.** Attacker text flows: Nexus notification → `getPost` → Postgres (parameterized `$1..$n` everywhere — verified in poller/reply/router/workers/budget/thread) → Redis Streams envelope → classifier/summary/factcheck prompts. Prompts use the `SYSTEM INSTRUCTIONS / USER_DATA` framing (`secure-prompts.ts`) plus a regex-based `InjectionDetector` that **never blocks** (by design) and only escapes delimiters when patterns match. There is **no shell, SQL, Cypher, file-path, or URL execution** of attacker text anywhere — no tool calls beyond OpenAI's hosted `web_search_preview`. Worst case remains the inherent one: attacker steers the LLM into publishing embarrassing text under the bot key (mitigated by truncation, wordlist, per-user rate limit, kill switch). SSRF: URL construction for Nexus is host-pinned (F13). Classifier prompt interpolates content into double quotes (`classifier.ts:124`) — framing-breakable but consequence-free. LLM narrative is published verbatim (`factcheck/worker.ts:316-326` uses raw model text as the verdict) — that's the main injection-impact surface; acceptable for staging with the kill switch live.

**5. Kill switch / admin.** `POST /api/admin/kill|resume` on the public listener, guarded by `ADMIN_TOKEN` header/Bearer (`health.ts:17-29`). Unset → 403 fail-closed (good). Not timing-safe, no brute-force protection (F2). CSRF irrelevant (header auth, no cookies; CORS `*` doesn't matter without credentials). Coverage: gates `publishReply` (all publishes funnel through `ReplyService.publish` → `pubkyService.publishReply`) and the poller; Redis failure → treated active (fail-closed, `kill-switch.ts:13-18`). Gaps: doesn't gate LLM spend (F17), doesn't gate `updateBotProfile` (F11), unreachable in default compose because the env isn't forwarded (F2).

**6. Rate limit / blacklist / budget.** Rolling-window ZSET, fail-closed on error (`rate-limit.ts:118-135`) — claim verified. Blacklist fail-closed on error too, but exact-match normalization (F10) and async-init race (F10). Budget: global daily cap, checked pre-classification and pre-summary; DB error propagates → routing fails → fail-closed. Bypasses: per-thread cap forgeable (F4); factcheck worker lacks the cap (F4); canned mode bypasses wordlist (F15).

**7. Privacy/logging.** No auth headers logged (request logger records method/url/ip/UA only — `server.ts:83-91`). Full pubkeys are logged in many places (rate-limit, blacklist, router) — more than strictly needed but consistent with the public-data model. Attacker content previews hit on-disk logs (F8); `failActionExecution` stores `error.stack` into Postgres (`summary/worker.ts:300-313`, `factcheck/worker.ts:379-392`) — internal only. Dev-mode stack traces to clients (F9). Health endpoints leak version/uptime/memory — standard, acceptable.

**8. Dependencies.** Top-level `express@4.21.2` (patched line), `path-to-regexp@0.1.12` (patched), `serve-static@1.16.2`/`send@0.19.0` (patched), `cookie@0.7.1`. `handlebars@4.7.8` dev-only via ts-jest — not reachable at runtime. Dead runtime deps pulling a second express (5.1.0) via `@modelcontextprotocol/sdk` — remove (F14). No known high/critical reachable at runtime identified from the lockfile.

**9. Docker/compose.** `.dockerignore` correctly excludes `.env`, `.env.*` (except example), logs, `.git`, AppleDouble files. Production stage: non-root `nodejs` user, dumb-init, no build tools — good. Issues: compose dev defaults mounted everywhere incl. production target (F1), secrets as env vars visible to `docker inspect` (inherent, note), DB/Redis exposed with default creds (F5), stale `PUBKY_AUTH_USERNAME/PASSWORD` envs still passed (code removed basic auth this branch — dead config, harmless), `ADMIN_TOKEN`/`BOT_DISABLED`/`PUBKY_SIGNUP_TOKEN` not forwarded (F2/F12).

**10.** jeb-slim ignored per instructions.

## Verdict: **FIX-FIRST**

Blocking for staging: **F1** (prod compose actually runs dev server with source+`.env` mounted and possibly development error mode), **F2** (admin endpoints brute-forceable / unusable as deployed), **F3** (no session-expiry recovery — guaranteed silent publish failure within ~30 days), **F5** (data-plane services exposed on LAN with default/no credentials). Strongly recommended in the same pass: **F4** (thread-cap forge + missing factcheck cap) and **F10** (blacklist normalization/init race). Everything else is Low/Info and can follow. The core key-handling and publish-path authorization (questions 1 and 3) are fundamentally sound — no critical findings.
