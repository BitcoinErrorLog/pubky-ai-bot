## New findings

### N-1 — Medium — F-10 origin check races the weekly enqueue: a lost race permanently fails the legitimate weekly article

- **Where:** ordering in `src/weekly/publish-article.ts`: `enqueueStandalonePost` inserts the claimable `publish_requests` row at `:65-70`, then a `handled_mentions` upsert (`:81-87`), and only then `finishWeeklySlot` writes `weekly_posts.mention_key` (`:88-93`). Boundary check added by the remediation: `packages/bot-kit/src/publish/publisher.ts:563-573` → terminal `store.markPublishFailed(row.id, "weekly approved_by requires matching weekly_posts.mention_key")`. Publisher poll cadence: `setTimeout(tick, 40)` (`publisher.ts:844`); rows are inserted `status='queued'`/`next_attempt_at ≤ now()`, i.e. immediately claimable.
- **What:** the publisher process can claim the weekly row in the ~1–5 ms window (two DB round-trips) between the publish-row commit and the `mention_key` commit. `weeklyOriginExists` then reads no match and the row is failed **permanently** (`failed` is never re-claimed). The subsequent `finishWeeklySlot` still writes `mention_key` + `status='queued'`, so `weeklyTick` never refires, and the next-day reaper (F-9) converts the row to `skipped`. Result: that week's article silently never publishes; the only signal is one `security_event` log line (`weekly_origin_missing`). Not attacker-steerable (timing only), but with a 40 ms poll against a multi-statement window the probability is on the order of a few percent per weekly enqueue — several lost articles per year, introduced by this remediation.
- **Fix (any one):** (a) treat `weekly_origin_missing` as retryable — `markPublishRetry(row.id, …, row.attempts)` like the F-6 deferral — so the next tick (after `finishWeeklySlot` commits) succeeds; (b) write `mention_key` at claim time: compute the content-seed hash before `claimWeeklySlot` and include it in the `INSERT`; (c) wrap `enqueueStandalonePost` + `finishWeeklySlot` in one transaction. (a) is one line and mirrors the F-6 pattern; add a regression test that flips the call order.

### N-2 — Low — Reaper/health counter lack a `post_uri IS NULL` guard; nothing ever sets `weekly_posts.status='published'`, so every published week ends up labeled `skipped`

- **Where:** `reapStaleWeeklyQueued` (`src/weekly/store.ts:324-329`) and `countStaleWeeklyQueued` (`:333-338`) match `status='queued' AND created_at < $1` with no `post_uri IS NULL`. No code path flips a successfully published week to `published`: `finishWeeklySlot` only writes `queued`/`skipped` in the success path (`publish-article.ts:88-93`; `published` only on the deduped `inserted=false` branch), and the post-publish hook writes only the `published` table (`db.ts:1129-1151`); the only other `weekly_posts` reader is the F-10 hook, which ignores `status`.
- **What:** a published Sunday article's row stays `queued` and is re-labeled `skipped` by the first tick after midnight. Operator-visible status for *every* published week becomes `skipped`, indistinguishable from an F-2-latch suppression (only `post_uri` discriminates, and only by hand). `staleWeeklyQueued` in health counts all published weeks between midnight and the next tick. Data/monitoring integrity only — no publish-path impact.
- **Fix:** add `AND post_uri IS NULL` to both statements (matching the wedge definition in F-9 and the latch guard at `loop.ts:71-73`); optionally set `status='published'` for weekly rows in `onStandalonePublished` so the dashboard/health can distinguish states.

### N-3 — Low — F-2 latch has no operator surface and no override path; one transient failure permanently suppresses the week

- **Where:** latch `src/weekly/loop.ts:66-78`; health exposes only `staleWeeklyQueued` (queued rows) — `reason.ts:78-84`; CLI `weekly run` cannot revive a latched week: `runWeeklySeries` → `enqueueWeeklyArticle` → `claimWeeklySlot` returns false → `inserted:false`, no re-enqueue (`publish-article.ts:44-57`, `cli.ts:57`).
- **What:** any single compose failure at fire time — including transient ones (model 5xx, Nexus timeout mid-run, DB blip) — latches the week to `skipped` with only a `log.warn`. Attacker-steerability is much reduced (secret-planted content is now redacted upstream: `updates-article.ts:42-44` for the updates prompt, `screenToolResult` redaction inside `sanitizeFeedbackQuote` for feedback quotes), so the residual is mostly self-inflicted transient failure, but there is no metric, no health field, and no documented operator recovery short of manual SQL (`DELETE FROM weekly_posts …`). Combined with N-2, even SQL status cannot distinguish a suppressed week from a published one.
- **Fix:** surface last-skipped week/series in health (after N-2's `post_uri` guard this is meaningful); consider one automatic retry with a short backoff before latching, or a `weekly run --force` that reclaims a `skipped` slot; document the manual recovery in `docs/weekly.md`.

### N-4 — Low — A7-2 static evidence-host allowlist excludes enabled operator knowledge sources (synonym.to, bitkit.to)

- **Where:** `src/drafts/evidence-uri.ts:5-13` (`STATIC_HTTPS_HOSTS` = pubky.app/github.com/api.github.com/pubky.org + app origin) vs enabled `sources.yaml` entries `synonym-to-site` (`https://synonym.to`, `cite_base: https://synonym.to/articles`) and `bitkit.to`. Consumers: `pubky-explained.ts:47-48` (chunks filtered; empty ⇒ `none: knowledge unavailable for that question`), `what-changed.ts:109-113` (URIs dropped from the citable set while the URLs still appear as prompt text `:122`).
- **What:** knowledge documents ingested from enabled operator sources on non-allowlisted hosts can no longer be cited or listed as evidence. `pubky-explained` may skip weeks it previously drafted; `what-changed` bullets citing those docs are dropped by `dropUnknownCitations`. Fail-closed (no security regression), but a behavioral regression for the current production manifest.
- **Fix:** derive the https allowlist from the operator manifest (`location`/`cite_base` hosts) passed into the generators, or add the manifest's configured hosts to the static set at config load.

### N-5 — Info — Display-name person-token exact equality has no length floor

- **Where:** `denylist.ts:60-61` (`p === n` with no minimum length) now receives Nexus display names (`reason.ts:548`). Publisher-side tokens remain z32-only (`src/publish.ts:66-81`), so this bites only at reason-side enqueue.
- **What:** a reply author whose display name equals a legitimate topic tag (e.g. "pubky", "paykit", "nexus") causes that self-tag to be silently dropped on replies to them. Fail-closed, single-reply blast radius; prefix matching is correctly floored at ≥8 chars (`denylist.ts:49-51`) so short common words ("bitcoin", 7) are safe.
- **Fix:** apply the same ≥8 floor (or a "contains space/uppercase in original" heuristic) to the equality branch for display-name tokens.

### N-6 — Info — Double security-event counting for secret-hit tag labels at the publisher

- **Where:** `publisher.ts:357-361` and `:436-440`: `rejectOpenTagReason` already increments per secret-scrubber hit (`policy.ts:54-57`), then the caller increments once more with `"secret-scrubber"`. Metrics only; denylist reasons are counted exactly once.
- **Fix:** drop the outer increment when `denied === "secret-scrubber"`.

## Probe answers (required new-issue review)

- **(a) F-1 newest-N cap:** safe. Capping changes only the collection *payload*; the PUT remains idempotent (deterministic `collectionPostId`/`collectionMentionKey`, `buildCollectionPost` validates before any DB write — `publisher.ts:246-251`), `assertCollectionItems` admits `length == cap`, and no published post or `publish_requests`/`published` row is deleted — only membership churns (oldest drops out). `reconcileCollections` enqueues the capped slice without trimming the stored `collection_items` list (`collections-maintain.ts:60-69`) — cosmetic drift that self-heals on the next append/rebuild; noted, not a finding.
- **(b) F-2 latch:** yes — one compose failure now permanently suppresses the week (by design), but the attacker trigger is largely closed (redaction upstream in both pipelines; the remaining latch causes are transient infra failures). The skipped row is **not** operator-visible beyond a warn log — filed as N-3 (and N-2 for status conflation).
- **(c) F-3:** no starvation of legitimate feedback — the 40-URI cap counts only *actually classified* URIs, stored/opted-out/blacklisted mentions are skipped before consuming it, and the mention-time path captures live traffic; >40 unprocessed genuine mentions per week is required to lose any. The daily-token pre-check is a soft TOCTOU budget: concurrent callers can each pass before either records, overshoot bounded by headroom + one classification per caller — acceptable; noted. Combined weekly spend can reach ~2× `JEB_WEEKLY_TOKEN_CAP` because classifier (`feedback:`) and updates (`weekly:updates:`) buckets are measured separately against the same cap value, with the daily budget as outer bound — doc-precision note for `docs/limits.md`.
- **(d) F-4/F-7 false positives:** publisher-side tokens are z32 ids only, so a legitimate tag must be an 8–20-char prefix of a 52-char z32 id to be denied — exactly the F-7 target, realistic false-positive probability negligible. Display-name equality can drop a topic tag at enqueue (N-5, fail-closed, no row failure). Row-fail consistency verified: artifact-tag denylist fail is terminal and re-enqueueable later (`insertArtifactTag` ON CONFLICT excludes `failed`, `publish-store.ts:305-316`); `tagOne` drops denied labels and `markTagsDone([])` when none remain (`publisher.ts:377-380`) — no wedged state.
- **(e) F-8 refetch:** bounded — one sequential `nexus.post` per quoted item, each timeboxed by the Nexus client timeout; item count is itself cap-bounded after F-3. No overall loop timebox (worst case items × per-call timeout; acceptable for a batch render). `null` view (incl. 404 — `nexus.ts:72`) drops the quote, so the deleted-quote issue stays closed whenever Nexus answers; transport throw keeps the quote (fail-open, test-pinned) — a deliberate, documented tradeoff that only reopens F-8(a) during Nexus outages. The 1 h skew rule is fail-closed for posts indexed >1 h late (dropped from windows) — acceptable; and `detected_at` used as the `indexed_at` fallback is coherent because ephemeral render items carry post-time `detected_at` (`classify-mentions.ts:140`, `tag-collect.ts:70`) while persisted rows are rendered in the same run via `extra` and then marked included.
- **(f) F-10 ordering:** **broken — filed as N-1.** The winner's `weekly_posts` row exists before enqueue, but `mention_key` is written only after; the publisher can claim in between and the fail is terminal.
- **(g) A7-4:** no. `generateFormat` is referenced only by `src/drafts/cli.ts` (main process) and `generate.ts`; `github.ts` (the sole `JEB_GITHUB_TOKEN` reader, `:59`) is reachable only through generators ← CLI. The dashboard POST path neither imports it nor takes `cfg` (test-pinned). Residual: the publish child is still spawned with full `process.env` (`main.ts:47`) — the token is present in the publisher's environment but unread; this is documented in `.env.example`/`docs/proactive.md` and matches the pre-existing "publish keeps the full env" design.
- **(h) A7-8:** session reuse is bound to the cookie value, not the admin credential: a CSRF token survives `ADMIN_TOKEN` rotation if cookies persist (accepted tradeoff; the token alone is useless without the admin cookie, and both are re-set on every GET). Rotation happens on cookie loss/invalidity, not per request — the multi-tab 403 nuisance is gone. Fixation requires planting a 64-hex cookie on the loopback origin; there is no cross-site set/send vector (`SameSite=Strict; HttpOnly; Path=/admin`, optional `Secure` behind TLS). Sound for the loopback threat model; if a stricter binding is ever wanted, derive the token as HMAC(admin-token, day) per the original A7-8 suggestion.
