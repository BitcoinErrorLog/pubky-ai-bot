## New findings

### F-N1 — Low — `markArtifactTagRetry` / `markArtifactTagFailed` are still unguarded: a revoke racing a failed attempt is silently resurrected and published

- **Evidence:** `UPDATE artifact_tags SET status='retry' … WHERE id=$1` with no status guard (`packages/bot-kit/src/publish/publish-store.ts:335-342`; same shape for `markArtifactTagFailed` `:344-349`); the tick calls `markArtifactTagRetry` on any non-`TagsBlockedError` from `applyArtifactTagOne` (`packages/bot-kit/src/publish/publisher.ts:699-702`). Sequence: claim (`publishing`) → operator `revokePostTag` (DELETE + `revoked`, `publisher.ts:280-281`) → publisher's PUT fails (homeserver error) **or the new rollback DELETE itself throws** (`publisher.ts:384`) → catch → `markArtifactTagRetry` flips `revoked`→`retry` → re-claim sets `publishing` → PUT → `markArtifactTagDone` rowCount=1 → `published`. The F-2 markDone guard is bypassed because the re-claim resets status. Pre-existing unguarded write; the remediation's rollback adds a second route into it. (Backstop: if the operator *re-applied* after revoking, the partial unique index `artifact_tags_active_uri_label` (`migrations/098:25-27`) rejects the `retry` flip and the tick swallows the error at `publisher.ts:711-713` — correct end state, noisy path. Without a re-apply, nothing stops it.)
- **Impact:** operator revoke fully and silently defeated when it lands in the claim→error window of a failing attempt; the tag is live under the bot key while the operator believes it revoked. Recoverable by re-revoking (row exists → DELETE + mark), and visible in `tags list`.
- **Fix:** guard both writes — `… WHERE id=$1 AND status <> 'revoked'` (retry/failed from a claim may legitimately target only `publishing` anyway) — and wrap the rollback `deleteArtifactTag` in try/catch + warn so a rollback failure never routes into `markArtifactTagRetry` (`publisher.ts:383-386`; same for `apply.ts:216,224`).

### F-N2 — Low — `revokePostTag` marks *after* the DELETE: a concurrent `done` landing in between leaves the object live with the row `revoked`

- **Evidence:** `publisher.ts:280-281` (DELETE, then `markArtifactTagRevoked`, itself unguarded `publish-store.ts:366-368`). Interleaving: op DELETE → pub PUT → pub `markArtifactTagDone` rowCount=1 (status was `publishing`) → op `markArtifactTagRevoked` → row `revoked`, homeserver object **exists**; the done=0 rollback (`publisher.ts:381-387`) never fires because done≠0. Silent divergence; contradicts `docs/publishing.md:46-48`'s promise. Related micro-window on the rollback side: the rollback re-read is keyed by `(post_uri,label)` latest-row (`getArtifactTag` `ORDER BY id DESC`, `publish-store.ts:351-356`), which correctly suppresses the DELETE once a re-apply inserts a newer row — the only remaining loss order is a rollback DELETE issued before the re-apply's INSERT but *landing* after its PUT (network reordering; sub-second, operator-recoverable).
- **Impact:** same user-visible effect as F-2 (a tag the operator wants gone stays published), in a two-statement window during an operator revoke racing the publisher.
- **Fix:** swap the order — `markArtifactTagRevoked` first, then `deleteArtifactTag`. Every publisher interleaving then either loses done (rollback DELETE fires) or wins done but is followed by the operator's own DELETE. A DELETE failure after marking is loud (CLI throws) and retryable, unlike the current silent divergence.

### F-N3 — Low — Kit `applyTags` with a transport can no longer finalize the row it PUTs; the hand-off is undocumented

- **Evidence:** the kit path never claims, so the row is `queued`; `markArtifactTagDone` now returns 0 for `queued` (`publish-store.ts:329`); `apply.ts:219-229` falls through and pushes the uri (success) leaving the row `queued`. Pre-remediation the unconditional markDone set it `published` (A5 evidence `apply.ts:225-227`). In Jeb the artifact-with-transport path is test-only (`src/tags.ts:47-50` passes no transport; live artifact PUTs go through `applyArtifactTagOne`), and the publisher tick eventually claims + re-PUTs (idempotent, hash of uri+label) + marks done, so Jeb converges. A non-Jeb kit consumer driving `applyTags` with a transport and no publisher loop gets rows stuck `queued` with the tag live, and `ApplyTagsResult` gives no hint. No test asserts the kit artifact success path's final row state.
- **Impact:** contract trap in the extracted capability (same tier as the original F-3).
- **Fix:** document on `applyTags`/TSDoc that a successful artifact PUT leaves finalization to the claiming publisher, or expose the row status in the result.

### F-N4 — Info — No reaper for `artifact_tags`: exhausted rows stick in `retry`/`publishing` forever

- **Evidence:** claim gate `attempts < $1` (`publish-store.ts:306`); stale-reclaim covers `publishing` only under the same cap (`:308`); the tick reaps `publish_requests` via `failExhaustedPublishes` (`publisher.ts:657`, `publish-store.ts:191-205`) — no artifact equivalent exists anywhere (grep-confirmed). A row that crashes out of its last claim stays `publishing` forever; a row whose last attempt errors stays `retry` forever — never `failed`. Answers the prompt's "row left `publishing` forever / is the reaper aware": the claim query's stale branch is the *only* reaper, and it is attempt-capped.
- **Impact:** operational — silently stuck rows invisible to triage. Pre-existing (claim/retry untouched by the remediation); surfaced by the rowCount-path review.
- **Fix:** add `failExhaustedArtifactTags(maxAttempts, staleMs)` mirroring `failExhaustedPublishes`, called each tick.

### F-N5 — Info — `revokePostTag` refusal orphans row-less tags (no pre-098 legacy case exists)

- **Evidence:** `publisher.ts:275-279`. Artifact tags as a feature shipped *with* migration 098, so "tags created before 098" cannot exist from this codebase — nothing legacy breaks. But a homeserver object lacking any row (row manually `DELETE`d; or the done=0-with-`current=null` branch at `publisher.ts:381-387`, which silently returns leaving the PUT live after a row delete) can no longer be revoked — the CLI refuses, and the error doesn't name the workaround (apply → let the publisher PUT → revoke).
- **Fix:** add `--force` to skip the row check (the DELETE is bot-keyspace-only anyway), or make the refusal message suggest apply-then-revoke.

### F-N6 — Info — Migration 102 flips *any* blank row to `failed`, including `published`/`revoked` ones

- **Evidence:** `migrations/102…sql:5-9` has no status filter. Pre-102, blank `approved_by` was reachable only via direct SQL (enqueue trims/requires non-empty since step 15, `publisher.ts:241-242`), so such rows should not exist; if a `published` blank row existed, the migration rewrites its audit state to `failed` and leaves the tag object live with no DELETE. Answers the prompt's migration questions — verified: the pre-UPDATE runs before `ADD CONSTRAINT` in the same per-file transaction (`src/infrastructure/database/migrator.ts:90-96`), so existing blank rows cannot reject the CHECK; `btrim('(missing)') <> ''` satisfies it; `failed` is valid because **no** CHECK on `artifact_tags.status` exists anywhere (`098:11-23`, grep-confirmed only 098/102 touch the table); the file is idempotent (ledger prevents re-run; manual replay matches 0 rows and re-DROP/ADDs safely).
- **Fix:** none required; optionally scope the UPDATE with `AND status NOT IN ('published','revoked')`, or keep as a deliberate suspicious-row flag.

## Verified properties

- **F-1 boundary is real, not cosmetic:** the blank-`approved_by` refusal fires before the kill-switch checks and before any PUT (`publisher.ts:360-368`), mirrors the A1 standalone refusal (`publisher.ts:449-458`), and the SQL CHECK is defense-in-depth below it. The `approved_by='(missing)'` sentinel satisfies the constraint; migration 102 is transactional and idempotent (above).
- **The done=0 rollback cannot delete a later re-apply's PUT (id-collision question):** a post-revoke re-apply inserts a *new* row (the `ON CONFLICT … WHERE status IN (active)` matches only active statuses, `publish-store.ts:287-294` + partial index `098:25-27`); the rollback re-read takes the *latest* row by id (`publish-store.ts:353-355`), sees the new row's non-`revoked` status, and suppresses the DELETE. Residual network-reorder window folded into F-N2.
- **Rollback DELETE runs under the same label/URI constraints as the PUT:** the label passed `scanForSecrets` before the PUT (`publisher.ts:371-378`, `apply.ts:206-211`) and `deleteArtifactTag` rebuilds via `artifactTagObject`, re-validating URI shape, label shape, and vocab (`apply.ts:139` → `:106-120`). It intentionally does *not* re-check kill switches — a kill switch must not trap a tag on the homeserver; the gates already passed for the PUT being rolled back.
- **`recordTagEvent({kind:"applied"})` throw has no live crash path:** the only production call site is `src/reason.ts:543` with literal `kind: "suggested"` (grep-confirmed across `src/` and `packages/`); the three former `applied` sites in `applyTags` were deleted by the remediation. Reason and publisher loops cannot hit the throw.
- **`parsePostUri` strictness is safe at every call site:** all external-input callers already handle the throw — `mentionKey` returns null (`types.ts:87-91,101-103,110-115`), `NexusClient.post` returns null (`packages/bot-kit/src/nexus/nexus.ts:33-37`); operator-input callers (`src/tags.ts:46,62`, `src/requeue.ts`, `src/corrections.ts:98`, `src/drafts/stats.ts:29`) fail loudly. Nexus emits canonical lowercase-z32/uppercase-post-id URIs, so no live caller relied on case-insensitivity; lowercase post ids (previously accepted via `/i`) are now rejected, which is strictly earlier failure on URIs that would 404 anyway. The returned author is `[a-z0-9]{52}` by construction and passes `Z32`/`assertAuthorId` everywhere (`nexus-schema.ts:44-47`); `toLowerCase()` is belt-and-braces. Residual inconsistency: exported `POST_ID` stays `/i` (`types.ts:45`) — used only by eval fixtures.
- **`markSelfTagsDone` cannot hit a row not owned by the reply:** the subselect joins `publish_requests→handled_mentions` on `mention_key` and filters `h.reply_uri=$1 AND p.status='published'`, latest first (`tag-store.ts:108-114`); `reply_uri` on `handled_mentions` is only ever written by the publisher for its own reply (`publisher.ts:587`), so a foreign URI matches nothing, and two requests sharing one reply URI (replace/overwrite flows) resolve to the latest published — still a row whose reply *is* this URI. It does overwrite unconditionally (no `tag_uris IS NULL` guard, no categories match) — same trust level as `tagOne`'s `markTagsDone`; in Jeb the self path is test-only.
- **Kill switches and scrub still gate every new PUT:** `publisher.ts:369-370`, `apply.ts:168,200`; tick-level gates unchanged (`publisher.ts:679,693`).
- **Test infrastructure is consistent:** `FakeTransport.deleteJson` overridable (`src/publish.test.ts:61`), `foreign` post id `00000000000TG` passes the strict regex (`:864`), Store implements the new `Promise<number>` signature (`src/db.ts:611-613`) and `markSelfTagsDone` (`:644-646`).
